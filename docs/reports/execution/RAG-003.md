## Decisions and open choices (ADR-0004 amendment)
Owner-decided (addendum): the retry policy, cap, single fallback attempt, daily-quota rule, `ALLOW_FALLBACK`, limits and
throttle. Choices I made inside those rules, for the owner to confirm at `99-VERIFY`:
1. Retryable statuses = the embedder's set (429, 500, 503, 504) plus timeouts and connection errors; 500 and 504 are
   beyond the owner's list.
2. 400/401/403/404 and an unparsable reply: raised at once as `other`, no retry, no fallback.
3. When both models fail, the error describes the **answer model's** failure and names the fallback's (a daily-quota
   primary whose fallback returns 503 stays a quota error; a 503 primary whose fallback is out of daily quota stays
   "unavailable"). The alternative, "raise the last error", would turn a transient 503 into "quota exhausted".
4. `retry_count` counts answer-model retries only; the fallback call is not a retry.
5. `GenerationError` is neither retried nor sent to the fallback.
6. `throttle_wait` was added next to the owner's `retry_wait`: at 13 RPM a full run is throttled, and without it
   `generate` would mix model time with throttle sleeping.
7. TPM and RPD are configuration only; the adapter throttles requests per minute.

## Explain it back
- **Retry, then fallback, and why those numbers.** The answer model (500 requests a day, 15 a minute) is cheap to
  retry, so it gets 3 attempts with exponential backoff and jitter; the fallback (20 a day, 5 a minute) is a safety net,
  so it gets one attempt. A daily-quota 429 is not retried because nothing changes before the reset. The evaluation runner
  turns the fallback off (`ALLOW_FALLBACK=false`) so every scored answer comes from one model; a mixed-model result would
  not be comparable. Alternative: fall back at once, which would burn the 20-a-day model on ordinary blips.
- **Errors are wrapped at the infrastructure edge, and `kind` is the GUI's kind.** The layer rules say the core, the
  application and the GUI never import `google.genai` or `httpx`; a raw `APIError` reaching the GUI would force it to
  parse status codes. `LLMQuotaError` / `LLMUnavailableError` / `LLMRequestError` carry `kind` = quota / unavailable /
  other, so the wiring is `AskQuestionError(error.kind, ...)`. When both models fail, the error describes the answer
  model's failure: a transient 503 must not be reported as "quota exhausted" just because the small fallback quota is gone.
- **One shared retry module, not a copy.** Both adapters need the same retry-after parsing, daily-quota detection and
  key redaction; two copies would drift. The embedder keeps the owner's earlier rule (no connection-error retry): moving
  code must not silently change accepted behaviour, and I had to correct that once.
- **Accounting is built for the latency report.** `retry_count` (answer-model retries) and `fallback_used` are separate
  because the latency report keeps retried and fallback answers out of the normal-call statistics (ADR-0004 D13);
  `retry_wait` and `throttle_wait` are reported apart from model time, so 13-requests-a-minute throttling is not mistaken
  for a slow model; unreported tokens are `None`, never 0, so a cost table cannot show a false zero.
- **The smoke check is a guarded experiment, not a demo.** Dev questions only (the eval firewall), the embeddings checked
  as cached first (0 embed requests), one attempt per step, a hard budget of 5 LLM requests, stop at the first provider
  error, and the LLM's own "insufficient" path exercised with `--gate-off`, a diagnostic that the eval runner never uses.
